# Investigation 01: Failed Logon Threshold Triggered — EventCode 4625

## Setup
- Attacker: N/A — self-generated test activity (see Classification)
- Target: LAPTOP-2KO5C8D6 (Windows host, local account: wreadtoad)
- Environment: Windows host running the Splunk indexer/search head and Universal Forwarder
- Log source: Splunk Enterprise (Windows Security Event Log via Universal Forwarder)

## 5 W's
- **Who** — Local account `wreadtoad`, logging in at the console of `LAPTOP-2KO5C8D6`
- **What** — 6 failed logon attempts (EventCode 4625, Logon_Type 2 - Interactive), Failure_Reason "Unknown user name or bad password." Manually generated by mistyping the account password at the Windows login screen (no scripts or tools used).
- **When** — 2026-09-18, 09:18:53.550 – 09:19:01.740 (6 attempts in ~8 seconds), falling inside the alert's 5-minute window bucketed at 09:15:00
- **Where** — `LAPTOP-2KO5C8D6` (local Windows host); Source_Network_Address `127.0.0.1` (loopback/local console, not a remote network source)
- **Why** — Exceeded the "Brute Force Detection" alert's threshold (3+ failed logons for one account within 5 minutes), which triggered an automated email notification

## Process
1. Received an email alert from the saved Splunk alert **"Brute Force Detection- Fauked Logon Threshold"** *(note: typo in the alert's own name — "Fauked" should read "Failed"; flagged for a fix, not corrected here since it lives in Splunk, not this repo)*.
2. Reviewed the alert's trigger condition (Number of Results > 0) against its detection search:
   ```
   index=homelab EventCode=4625 Account_Name=wreadtoad
   | timechart span=5m count
   | where count>3
   ```
3. Re-ran the detection search over the last 24 hours to confirm the trigger. Found one 5-minute bucket (2026-09-18 09:15:00) with `count=6`.
4. Pulled the individual raw events to inspect the fields needed for triage:
   ```
   index=homelab EventCode=4625 Account_Name=wreadtoad
   | table _time, Account_Name, Logon_Type, Failure_Reason, Source_Network_Address
   ```

## Evidence
- 6 matching events, timestamps 09:18:53.550–09:19:01.740 on 2026-09-18
- Logon_Type = `2` (Interactive)
- Failure_Reason = `Unknown user name or bad password.`
- Source_Network_Address = `127.0.0.1`
- Account_Name (target) = `wreadtoad`; Subject/machine account = `LAPTOP-2KO5C8D6$`

## Classification
**True Positive (alert) / Non-Malicious (activity).** The alert's detection logic worked exactly as designed — it correctly identified 6 failed logons for one account inside a 5-minute window and fired. The underlying activity, however, was confirmed self-generated: the account owner manually mistyped the password at the local console while testing the alert. The Logon_Type (2 - Interactive) and Source_Network_Address (127.0.0.1, loopback) both confirm this came from the machine's own console, not a remote attacker — a genuine remote brute-force attempt against this same alert would instead show Logon_Type 3 (Network) and an external source IP.

## Severity
**Low.** No remote source, no successful unauthorized logon, and no account lockout occurred. The activity was confirmed intentional and benign.

## Escalation
No escalation required. Tier 1 disposition: close as benign/test activity. Documented here as a baseline example of what a *benign* trigger of this alert looks like, to compare against if the same alert ever fires from a real Logon_Type 3 / external-IP source.

## Takeaway
Threshold-based alerts like this one only tell you *that* a condition was met — not *why*. Pivoting into Logon_Type and Source_Network_Address before writing a disposition is what actually separates a benign self-test from a real credential-stuffing or brute-force attempt using the same detection logic. This investigation also served as an end-to-end validation that the detection search, the alert schedule, and the email notification pipeline are all working correctly.
